# Real-Time Video Conferencing System

Multi-party video conferencing for the CS305 (Computer Networks, SUSTech) course project.
There is a Go server that handles meetings over TCP and relays media over a single UDP port,
and a Python asyncio client with a split-screen window, chat, and fake camera/microphone input
so it can also run headless.

It covers everything in the course spec: create, join, list, leave and cancel meetings; text
chat with the sender's name and a timestamp; multi-party video and audio; several meetings at
once without leaking media between them; and peer-to-peer media for two people, switching to
the server relay when a third person joins (and back again).

## Background

We first built this in 2024 as a team, in Python on raw sockets. That version is still on the
`main` branch and, unchanged, in [`legacy/`](legacy/), so every comparison below can be rerun
from this repo. In 2026 I rebuilt it on this branch (`v2`) to fix what I didn't like about the
old design: frames sent as one huge UDP datagram, audio that fell further behind with every
extra talker, pickle on the wire, and clients identified only by IP address.

More detail lives in `docs/`:

- [`ENGINEERING_NOTES.md`](docs/ENGINEERING_NOTES.md): each change, why I made it, what I measured, and the trade-off
- [`PROTOCOL.md`](docs/PROTOCOL.md): the wire format (byte layouts and JSON message fields)
- [`BENCHMARKS.md`](docs/BENCHMARKS.md): how the benchmarks work, all results and their caveats

## Results

Everything was measured on one shared 4-vCPU Linux VM, on loopback or in network namespaces,
with three runs per point. The tables show the median with the range of the three runs in round
brackets. B1 is different: it pools the frames of all three runs and shows a Wilson 95%
interval in square brackets. The tables are generated by `bench/render.py`.

The 2024 version sends each 31 kB frame as one UDP datagram, which IP splits into 21 or 22
fragments, so losing any one fragment loses the whole frame. v2 splits a frame into packets of
at most 1232 bytes, adds one XOR parity packet per four fragments, and a receiver that is still
missing a packet asks the server to resend it (RTCP generic NACK). FEC and NACK together are
the client's default.

arrives after the next frame is already complete and the receiver drops the older frame:

The 2024 client plays every talker's audio one after another on a blocking stream, so with two
or more people talking, playback falls behind and the same thread stops reading video. v2 mixes
audio on the server (mix-minus: everyone gets the sum of the others) and sends each receiver a
single stream. Its 119 ms is just the buffering it is set up for: 40 ms of jitter buffer on the
server, 60 ms of playout delay on the client, and up to 20 ms to the next tick on each side.
No audio hardware was available, so both ends are simulated; see
[`BENCHMARKS.md`](docs/BENCHMARKS.md#b2-multi-talker-audio) for what that assumes.

<!-- END GENERATED summary_b3 -->

I profiled the server with pprof first: most of its CPU went to system calls. Batching reads
and writes with `recvmmsg`/`sendmmsg` and then sending each sender's packets to a receiver as one
UDP GSO message raised the largest size that passed in every repeat from 160 to 272
participants. About half of the CPU saving is softirq time of the receivers' loopback receive
path, which the kernel charges to the server's core; without it the server's own CPU went down
about 15%.

This comparison doesn't favour v2: for the same media it sends about 19 times as many packets as
the 2024 version, because loopback's 64 KiB MTU lets the old version's huge datagrams through
without fragmenting. That is the price of packets that are safe on a real 1500-byte path.

## Architecture

```mermaid
flowchart LR
    subgraph clients["Python clients (asyncio)"]
        A["alice"]
        B["bob"]
        C["carol"]
    end
    subgraph server["confserver (Go)"]
        SIG["signaling<br/>TCP :6100<br/>reader + writer goroutine<br/>per connection"]
        REG["room registry<br/>life cycle, P2P/relay decision"]
        RT["media router<br/>UDP :6100<br/>SSRC + address check,<br/>rate limit, SFU forwarding,<br/>NACK resends, recvmmsg/sendmmsg + GSO"]
        MIX["mixer per room<br/>20 ms tick, mix-minus"]
        MET["/metrics, pprof<br/>127.0.0.1:6101"]
    end
    A & B & C <-->|"length-prefixed JSON:<br/>rooms, chat, roster, mode"| SIG
    SIG --> REG
    REG -->|"immutable view,<br/>atomic swap"| RT
    RT -->|"audio"| MIX
    A & B & C <-->|"RTP: video fragments, audio,<br/>XOR parity; REGISTER; RTCP NACK"| RT
    MIX -->|"one mixed stream<br/>per receiver"| RT
```

- **Control plane:** one TCP port. Every message is a 4-byte length followed by a JSON object.
  The server owns all room state: it hands out participant ids, SSRCs and a random session
  token, stamps chat messages with the sender's name and its own clock, and decides whether a
  room runs peer-to-peer or through the relay.
- **Media plane:** one UDP port for all rooms. A client first sends `REGISTER` with its token
  from its media socket (repeated until acknowledged, a bit like a STUN binding request). After
  that the server only accepts that client's SSRC from that address and only forwards within
  its room, so meetings stay isolated and spoofed packets get dropped. Packets use the RTP
  header, so Wireshark can decode them ("Decode As... RTP").
- **Video:** one JPEG per frame, split into fragments of at most 1200 bytes of JPEG plus one XOR
  parity packet per four fragments. Every UDP payload is at most 1232 bytes, so nothing gets
  IP-fragmented on a 1500-byte path. The server forwards fragments as they are (SFU-style) and
  keeps the last 256 video packets of each sender for retransmission.
- **Audio:** 16 kHz mono PCM in 20 ms frames. Every 20 ms the server mixes all active senders
  and subtracts each receiver's own frame (mix-minus), so a receiver always gets one stream no
  matter how many people talk. The client plays it through a 60 ms jitter buffer with loss
  concealment.
- **Mode switching:** with exactly two registered members the server sends each one the other's
  address and forwards nothing. With three or more it relays. After a switch, clients accept
  media from both paths for 2 s and the server keeps relaying for 1 s, so nothing in flight is
  lost.
- **Hot path:** when rooms change, a separate goroutine rebuilds the routing table and swaps it in
  atomically, so the forwarding goroutine never waits on the registry. Forwarding video takes no
  lock and allocates nothing per packet. On Linux the media socket reads up to 64 datagrams per
  `recvmmsg` and sends with `sendmmsg` and UDP GSO (`server/internal/udpio`); other platforms use
  one system call per datagram.

### Joining a meeting

```mermaid
sequenceDiagram
    participant C as client
    participant S as server (TCP 6100)
    participant M as media router (UDP 6100)
    C->>S: hello {name, version}
    S-->>C: welcome {client_id, media_port}
    C->>S: join_room {room_id}
    S-->>C: joined {audio_ssrc, video_ssrc, mixer_ssrc, token}
    S-->>C: roster (to every member)
    loop every 200 ms until acknowledged, then every 5 s
        C->>M: REGISTER {token}
        M-->>C: REGISTER_ACK {observed address}
    end
    S-->>C: mode {relay} or {p2p, peer address}
    C->>M: RTP video fragments + parity, 20 ms audio frames
    M-->>C: other members' video, mixed audio without the receiver's own voice
```

### Switching between peer-to-peer and relay

```mermaid
sequenceDiagram
    participant A as alice
    participant B as bob
    participant S as server
    participant C as carol
    Note over A,B: two registered members
    S-->>A: mode p2p, peer = bob's address
    S-->>B: mode p2p, peer = alice's address
    A->>B: media directly (server forwards nothing)
    C->>S: join_room, then REGISTER
    S-->>A: mode relay
    S-->>B: mode relay
    S-->>C: mode relay
    Note over A,C: clients accept both paths for 2 s
    A->>S: media
    S->>B: alice's video + mix of alice and carol
    S->>C: alice's video + mix of alice and bob
    C->>S: leave_room
    S-->>A: mode p2p, peer = bob
    S-->>B: mode p2p, peer = alice
    Note over S: keeps relaying for 1 s
```


## Running it

### Server (Go 1.24+, Linux, macOS or Windows)

```sh
cd server
go build -o bin/confserver ./cmd/confserver      # Windows: go build -o bin\confserver.exe .\cmd\confserver
./bin/confserver                                  # loopback only: 127.0.0.1:6100 (TCP and UDP)
./bin/confserver -control-addr 0.0.0.0:6100 -media-addr 0.0.0.0:6100   # serve a LAN
```

Useful flags (`-h` lists all of them): `-p2p=false` always relays, `-pprof` turns on
`/debug/pprof/` next to `/metrics` (127.0.0.1:6101), `-log-format json` for JSON logs,
`-udp-batch 1` turns batching off, `-udp-gso=false` keeps batching without GSO, and
`-nack-buffer 0` turns off retransmission.

With Docker (static binary, non-root user):

```sh
docker build -t confserver -f server/Dockerfile server
docker run --rm -p 127.0.0.1:6100:6100/tcp -p 127.0.0.1:6100:6100/udp \
  -p 127.0.0.1:6101:6101 confserver
```

The server has no authentication or encryption, so only publish it on a network you trust.

### Client (Python 3.11+, [uv](https://docs.astral.sh/uv/))

```sh
cd client
uv sync                                                   # numpy and Pillow; no OpenCV or PyAudio
uv run confclient --name alice --fake-media --create standup
uv run confclient --name bob --fake-media --join 1
uv run confclient --name carol --fake-media --join 1
```

`--fake-media` swaps the camera for a moving test pattern and the microphone for a tone. For a
real camera and microphone run `uv sync --extra video --extra audio` (OpenCV and PyAudio;
PyAudio needs PortAudio: `brew install portaudio` or `sudo apt install portaudio19-dev`).

Commands at the prompt (or non-interactively with `--script "cmd; cmd"`):

```
list | create [title] | join <id> | leave | cancel | chat <text> | video on|off |
audio on|off | status | sleep <seconds> | help | exit
```

With two people the client prints `* media mode: peer-to-peer with ...`. When the third joins,
everyone switches to `* media mode: server relay`.

## Network limits

I developed this on a shared campus network, so everything binds to loopback by default and
every part has a traffic cap:

| Part | Default limit | Flags |
|---|---|---|
| Server sockets | 127.0.0.1 only | `-control-addr`, `-media-addr` |
| Media in, per client | 8 Mbit/s including headers (token bucket); the excess is dropped and counted | `-max-ingress-kbps`, `-ingress-burst-kib` |
| Retransmissions | 8 Mbit/s per requesting client, from a separate budget; a NACK must come from the requester's own address and name video in its room | `-max-rtx-kbps`, `-nack-buffer` |
| Media bindings | an address is only bound after it echoes a server nonce; `REGISTER`s limited per member, per source and in total | `-max-registers-per-sec`, `-binding-timeout` |
| Control plane | 16 per room, 256 rooms, 1024 clients; 50 frames/s per connection; timeouts for `hello` and idle connections | `-max-room-size`, `-max-rooms`, `-max-clients`, `-control-rate`, ... |
| Client upload | 6000 kbit/s of video and audio; feedback packets have their own small budget | `--max-send-kbps` |
| Load generator | loopback only unless `-allow-remote`; caps on total Mbit/s, packets/s, participants and run length | `-allow-remote`, `-max-mbps`, `-max-pps`, ... |

The benchmarks run entirely inside network namespaces on one machine.

## Tests

```sh
make test     # gofmt, go vet, staticcheck, ruff, mypy, then go test -race and pytest
make fuzz     # 30 s of Go fuzzing per decoder
make ci       # the same steps as the CI workflow's Linux jobs (run it in a fresh clone)
```

- **Go:** table-driven unit tests (room state machine, mode decisions, mixer, FEC recovery,
  NACK budgets), eight fuzz targets for the decoders, and integration tests that start the
  server in-process and drive fake clients through the whole meeting life cycle, P2P to relay
  and back, meeting isolation and spoofed packets.
- **Python:** unit tests for the packetizer, FEC, frame assembly under loss and reordering, the
  audio jitter buffer and rate limits, plus end-to-end tests (`pytest -m e2e`) that start the Go
  server and run three headless clients.
- **Shared test vectors:** Go and Python both check against the same 63 golden vectors in
  `protocol-testdata/vectors.json`, so the two sides can't drift apart.
- **CI:** [`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs lint, the Go race tests,
  short fuzzing, one run of every benchmark, the client tests on Python 3.11 and 3.13, the Go
  and Python tests on macOS and Windows, and a build and smoke test of the Docker image.

Testing on more than one OS found real bugs. On Windows a datagram longer than the read buffer
comes back as an error instead of being truncated, and the media router backed off on it, so
anyone sending oversized packets could stall forwarding on a Windows server. Separately, the
client couldn't register its media on Python 3.11 at all until the 3.11 job caught it.

## Benchmarks

Each experiment is one command and writes JSON to `bench/results/`. B1 to B3 need root for
network namespaces and nftables. Timing-sensitive steps take a lock file
(`${XDG_RUNTIME_DIR:-/tmp}/cs305-bench.lock`, or `BENCH_LOCK`) so they don't overlap with other
jobs on the machine.

```sh
sudo bench/run_b1.sh            # B1 packet loss
sudo bench/run_b2.sh            # B2 multi-talker audio
sudo bench/run_b3.sh            # B3 relay capacity
sudo bench/profile_b3.sh        # CPU profiles at 128 participants
bench/run_micro.sh              # Go microbenchmarks
(cd client && uv run --group bench python ../bench/render.py)   # tables and plots
```

The 2024 code runs unmodified: `bench/legacy_harness/` provides stand-ins for its camera,
PyAudio and pyautogui imports and forces relay mode.

## Limitations

- I had no camera, microphone or speaker while building this. The OpenCV and PyAudio adapters
  are thin and haven't been tested with real hardware; all tests and benchmarks use synthetic
  media.
- Video is one JPEG per frame. Simple and loss-tolerant, but about 4 Mbit/s for 480x480 at
  15 fps, much more than a real video codec would need.
- No encryption. A member's media binding only moves after the new address echoes a server
  nonce, so an off-path attacker can't redirect it, but someone who can read the traffic can.
- P2P uses the address the server sees, with no ICE/STUN/TURN, so it only works on a LAN or
  behind permissive NATs. Otherwise run the server with `-p2p=false`.
- No congestion control or adaptive bitrate, audio isn't retransmitted, and the retry interval
  is fixed at 30 ms.
- The host role isn't handed over when the host leaves; the room closes once it is empty.
- All benchmarks ran on one shared VM with emulated loss and delay, not a real network.
